# 当前项目代码审查指南

编写日期：2026-10-30。适用项目：s-light notes v2，当前开发版本以 `package.json` 为准。

这份指南用于从产品要求出发，检查桌面端、Android 和 Web/PWA 的实现，找出能够说明触发条件与用户影响的 bug。审查优先关注笔记丢失、静默覆盖、保存与退出竞态、同步边界和原生权限，再检查一般交互与维护问题。

审查开始时重新核对工作区、测试入口和项目约束。历史测试记录只证明其对应提交、平台和用例，不自动证明当前改动已通过。

## 1. 开始前：明确审查对象

在仓库根目录执行以下只读命令：

```sh
git status --short --branch
git log -1 --format='%h %s'
git diff --stat
git diff
git diff --cached
rg --files docs app/js src-tauri/src tests
```

记录以下信息：

- 当前分支、提交、未提交改动和新增文件。`git diff` 不包含未跟踪文件的内容，应根据 `git status` 单独读取。
- 本次是全项目审查，还是针对某个功能、提交或差异的审查。
- 目标平台与存储模式。桌面 Markdown、Android 原生文件、Web/PWA IndexedDB、浏览器 FSA 应分别分析。
- 允许的操作范围。审查阶段默认只读；确认问题后，按用户的修复要求修改并验证。

不要为了得到干净工作区而重置、暂存或删除已有修改。当前工作区可能包含尚未提交的修复，应连同其调用方、测试一起阅读。

### 3.2 追完整调用链

以“编辑后保存”为例，沿下列路径检查：

```text
用户输入
  → 编辑器将内容标为 dirty，并调度自动保存
  → 主窗口/便签保存队列或移动端保存队列
  → 存储服务 / Tauri invoke
  → Rust 文件操作，或 Android Rust → Kotlin → NoteStore
  → 写入完成 / 返回错误
  → 更新 ID、版本、dirty、列表和同步扫描
```

每经过一层都问：参数从哪里来、状态由谁修改、失败如何返回、调用者是否等待、完成后是否仍然属于原来的编辑会话。

特别注意保存函数末尾调用的列表刷新、工具栏更新和事件回调。它们也可能修改编辑权限、当前笔记或关闭状态，不能只审查实际写文件的函数。

## 4. 按风险审查实现

### 4.1 数据保存、回收站和导入导出

- [ ] 新建和更新明确区分；已有笔记可保存为空，空草稿不意外创建文件。
- [ ] 更新携带加载时的内容版本；过期、已删除和冲突来源不会被强制覆盖。
- [ ] 同一编辑器的保存按顺序执行；首个保存返回的新 ID、版本供后续保存使用。
- [ ] 保存期间继续输入后，新内容仍标为 dirty；旧保存结果不会清掉新输入。
- [ ] 保存成功返回时，写入结果与返回版本对应；失败时保留内容并给出可重试路径。
- [ ] 切换笔记、新建、回收站、导出和关闭操作，都检查保存结果及剩余 dirty 状态。
- [ ] 同名导入、恢复和重复删除保留所有版本；目标在检查后被创建时也不会被覆盖。
- [ ] 复制失败不会删除源文件；移动的删除步骤失败后，两份文件与错误可被解释。
- [ ] 路径校验覆盖目录穿越、符号链接、异常文件类型、中文及跨平台文件名。
- [ ] 导出排除回收站、设置和同步凭据；内容校验与清单相符；导入失败回退范围明确。

区分两个问题：唯一名称检查解决通常的同名场景；独占创建等文件操作语义解决检查与实际写入之间的竞态。仅使用 `exists()` 后再覆盖写，仍有风险。

### 4.2 异步切换和多窗口退出

- [ ] 每次读取记录导航序号或编辑会话，返回时检查是否过期。
- [ ] 读取等待期间的新输入不会被迟到的读取结果覆盖。
- [ ] 回收站切换或清空编辑器也能使此前未完成的读取失效。
- [ ] 主窗口和便签同时编辑时，干净编辑器可刷新，脏编辑器保留内容并提示冲突。
- [ ] 关闭等待保存；保存失败或输入法仍在组合输入时，能够否决关闭并恢复交互。
- [ ] 应用退出等待所有窗口确认；已确认的窗口保持冻结，直到退出完成或被取消。
- [ ] 列表刷新、冲突状态更新、快捷键、粘贴和工具栏不会绕过退出冻结。
- [ ] 退出取消后恢复正确的编辑权限；回收站与冲突内容仍只读。
- [ ] 已取消退出的旧确认，不会关闭下一次退出流程中的窗口。
- [ ] 关闭主窗口保留其他便签和必要进程；停止同步只处理本应用管理的实例。

将并发场景写成时序更容易发现问题，例如：

```text
主窗口请求退出 → 冻结 → 保存成功 → 刷新列表 → 确认完成
另一便签仍在保存 ───────────────────────────→ 确认完成 → 应用退出
```

逐点检查主窗口是否在等待期间重新可编辑，以及此时的新输入由谁负责保存。

### 4.3 编辑器与输入法

- [ ] 中文组合输入期间，不保存半成品，不触发误切换或误退出。
- [ ] 未编辑内容往返保持一致；编辑一个块不会重写其他块的空行、不支持语法或正文。
- [ ] 代码块语言与围栏、嵌套列表、列表起始编号、行内代码、链接和图片有对应例子。
- [ ] 撤销和重做会正确更新 dirty；切换笔记后不会串用旧撤销状态。
- [ ] 粘贴 HTML、拖入内容、链接和图片 URL 不引入可执行内容或未经允许的原生路径访问。
- [ ] 长笔记与搜索结果保持内容一致；性能结论注明数据规模和测量方式。

### 4.4 同步与凭据边界

- [ ] 引擎启动、停止、错误、断网时，界面状态与实际进程一致，本地保存仍可用。
- [ ] 配对预览不写配置；确认 token 有有效期、只能使用一次，并在写入前复查实际状态。
- [ ] 配对只共享规定的笔记文件夹；失败时回退本次修改，不破坏原有配置。
- [ ] 前端不能通过参数获得 API Key，或任意指定原生代理地址、REST 路径和文件路径。
- [ ] 同步事件轮询可停止，快速关闭重开不会重复启动，旧事件结果不会污染新会话。
- [ ] 冲突文件明确标记且受只读限制；保留副本后正文一致。
- [ ] 离线修改与重连保留文件；退出后无本轮遗留引擎进程。

### 4.5 Android 和原生命令授权

- [ ] 原生存储初始化失败显示错误并阻止新建，不静默回退到 IndexedDB。
- [ ] Tauri 命令声明、注册与 capability 一致；主窗口、便签、Android 各有正确的最小权限。
- [ ] 便签不获得同步配置或凭据命令；Android 不携带桌面浮窗、快捷键或 sidecar 依赖。
- [ ] `DocumentsProvider` 只开放允许的笔记文件，不开放回收站、身份、配置、日志或密钥。
- [ ] 相机、通知、附近设备权限拒绝和撤销分别处理；本地笔记始终可用。
- [ ] 前台服务、worker 和进程生命周期争用同一引擎时，不会误停其他使用者的会话。
- [ ] 系统返回、切后台、Activity 重建和强行停止后的恢复均保持笔记及设备身份。
- [ ] 版本号、Android 安装版本码、ABI 和签名升级关系可核对；不以旧二进制冒充当前源码产物。

## 5. 用最小测试验证推断

### 5.1 测试环境约束

以根目录 [AGENTS.md](../../AGENTS.md) 和 [无界面测试说明](../HEADLESS_TESTING.md) 为准：

- 默认使用 Docker 和无界面 QEMU；Apple Silicon 日常选择 ARM64 Linux。
- 不在宿主机启动产品、浏览器或模拟器窗口，不接管焦点、键盘或剪贴板。
- Parallels 或 Mac 真机验收需为本次测试另行征求同意，历史授权不自动延续。
- 使用临时笔记和测试身份，不挂载用户笔记、签名密钥或同步身份。
- 优先运行少量相关测试；完整回归、原生构建、跨架构和性能测试按实际风险追加。
- 测试后删除自己的容器，停止本轮启动的虚拟机并清理临时数据；保留镜像缓存。

### 5.2 日常入口与选择方式

以下命令在仓库根目录执行。需要 Docker CLI、Colima 和 QEMU 已安装；镜像与依赖首次准备可能需要网络。测试容器运行阶段禁用网络。

```sh
# 已运行时直接复用；启动前先检查 slight-qa 的状态。
colima list
colima start slight-qa --vm-type qemu --arch aarch64 --cpu-type host \
  --cpus 2 --memory 2 --disk 12 --runtime docker \
  --mount none --mount-type 9p --activate=false --ssh-config=false --binfmt=false

# 不指定模块时，运行 native-shell、desktop-editing、reliability。
npm run test:container

# 按本次范围选择；以下是不同场景的示例，不要求全部执行。
npm run test:container -- desktop-editing desktop-storage
npm run test:container -- editor
npm run test:container -- reliability mobile-storage-service
npm run test:container -- sync-service sync-center
npm run test:container -- settings

# 无论测试成功或失败，都完成环境清理。
# 只停止本轮自行启动的 slight-qa；若开始前已运行，保留其原状态。
colima stop slight-qa
```

`scripts/test-container.mjs` 默认使用 `colima-slight-qa` context，并通过专用 Dockerfile 复制有限源码。它不会切换全局 context，不挂载宿主机目录；测试容器退出自动删除，异常时也会尝试删除自身容器。

容器不是完整仓库镜像。`structure` 套件被入口明确拒绝，Rust 库测试也不由此入口执行。其他读取原生源码的套件，选用前先确认 Dockerfile 包含其所需文件；不要把缺少测试上下文误判成产品 bug。

| 改动或疑点 | 首选验证 | 仍需注意的边界 |
| --- | --- | --- |
| 保存队列、切换、回收站、退出冻结 | `desktop-editing`、`desktop-storage` | DOM 模拟不能证明真实 IPC、窗口销毁与操作系统退出 |
| Markdown、输入法事件、撤销和 URL | `editor`，涉及移动端时加 `reliability` | 模拟事件不能替代厂商输入法或真实键盘验收 |
| 桌面文件操作 | `src-tauri/src/desktop.rs` 内 Rust 定向测试 | JS mock 不会执行 Rust；需隔离 Rust 环境或原生 CI |
| 设置、同步界面和桥接 | `settings`、`sync-service`、`sync-center` | mock 返回成功不代表真实配置和双向文件交换 |
| 原生缓存恢复 | `native-shell` | Windows WebView2 行为仍需原生证据 |
| Android 权限、生命周期或升级 | 对应边界测试及 `scripts/test-android-headless.py` | 按需准备隔离 AVD、SDK 和匹配 APK；细节见无界面测试文档 |
| 真实 P2P 协议或安装版行为 | 原生 CI 中的双引擎测试或定向安装版验收 | 两引擎同机测试不替代两台桌面设备的安装包 UI 验收 |

### 5.3 怎样补有价值的回归测试

1. 使用两三条临时笔记即可表达问题；先确定应保留的内容与文件集合。
2. 用可手动释放的 Promise 控制保存和读取顺序，稳定复现竞态，避免依赖任意时长的睡眠。
3. 注入保存失败、过期版本、目标已存在、连续点击或退出取消，检查失败后的状态。
4. 断言用户结果：正文保留、文件不被覆盖、导航被阻止、编辑权限正确、错误可见。
5. 跨模块问题保留真实调用链，只在原生边界等必要位置替换依赖。例如验证退出冻结时，应执行真实列表刷新，而非把 `refreshNoteList()` 全部 mock 掉。
6. 修改前能复现、修改后能通过时，记录前后差异。若仅从源码确认，应明确写“静态确认”。

Rust 完整集成测试应在准备好依赖的隔离环境或原生 CI 中执行。以下是供该环境使用的定向命令示例，不在宿主机直接运行：

```sh
cargo test --manifest-path src-tauri/Cargo.toml --locked --lib trash
cargo test --manifest-path src-tauri/Cargo.toml --locked --lib move_rejects_existing_destination
```

从源码提取纯 Rust 函数执行的小型测试，可以补充文件操作证据，但报告应注明提取范围，不能据此宣布完整 Tauri 库编译、命令注册或原生 UI 已通过。

需要原生平台证据时，查看 `.github/workflows/desktop-validation.yml`。当前工作流默认选择 Windows/Linux，也支持按平台选择；包含 Mac 的运行仍遵守项目询问要求。复用旧安装包的 `package_run` 只适用于产品源码无差异的测试脚本改动，产品改动需要新产物。

## 6. 本轮审查提供的三个回归样例

以下样例来自 2026-10-29 的审查与修复，用于后续审查时防止退化。代码是否已合入、产物是否已更新及当前是否通过，应重新核对本次提交与测试。

| 样例 | 触发步骤 | 必须保留的行为 | 对应测试位置 |
| --- | --- | --- | --- |
| 切换回收站丢失编辑 | 编辑后在自动保存前切换；或保存失败后切换 | 等待保存；失败或仍有新输入时不清空；重复点击和迟到读取不破坏状态 | `tests/desktop-editing.test.mjs` |
| 回收站同名覆盖 | 删除 `a.md`，新建另一份 `a.md` 后恢复；再次删除同名文件 | 保留现有文件和回收副本，以编号区分；目标在写入前出现时拒绝覆盖并保留源文件 | `src-tauri/src/desktop.rs` 的 `trash_and_restore_preserve_same_named_notes`、`move_rejects_existing_destination_without_changing_either_file` |
| 退出保存后重新可编辑 | 主窗口退出保存完成且刷新列表，另一便签仍在保存 | 保持编辑器冻结并拦截编辑动作；取消退出后按原有只读状态恢复 | `tests/desktop-editing.test.mjs` |

它们分别说明：切换入口必须检查保存、文件操作必须考虑同名及竞态、保存完成后的界面更新也需要审查。单个函数的正常路径测试通过，仍可能漏掉这些流程组合。

## 7. 写出可复核的问题报告

按影响排序。优先级采用以下约定，具体仍结合触发概率、数据可恢复性和影响范围判断：

| 级别 | 判断依据 |
| --- | --- |
| P0 | 广泛且立即发生的数据破坏或严重权限突破，需要立即阻断 |
| P1 | 可触发的数据丢失、静默覆盖、关键功能不可用或明显安全边界失效 |
| P2 | 有条件的功能错误、状态不一致，通常存在可行绕过方式 |
| P3 | 较低影响的交互、文案或维护问题 |

每个问题使用下面的结构：

```text
[P1] 标题：描述具体错误行为

位置：相对路径及当前行号，尽量定位到导致问题的少量代码
前提：平台、存储模式、初始文件/窗口状态
步骤：最短可复现操作，必要时给出异步返回顺序
预期：对应哪条产品行为约束
实际：哪份内容或哪个状态被错误修改
影响：数据损失、范围和恢复可能性
原因：完整调用链中导致偏差的判断或状态修改
证据：静态分析 / 容器复现 / 原生运行，附命令与关键结果
建议：最小修复方向，以及需要保留的回归用例
未验证：尚未运行的平台、原生行为或集成环节
```

分开记录已确认问题、待验证疑点和文档/发布事项。没有明确触发条件和用户影响的风格偏好，不应混入 bug 列表。引用代码行号前重新核对当前文件，避免使用修改前的位置。

测试报告记录提交与未提交差异、环境、实际命令、结果及局限。既有 CI 应核对提交、平台、用例和产物摘要；“构建成功”“单元测试通过”“安装版验收通过”分别陈述。
